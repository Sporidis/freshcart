Basket · Interaction study — how we got there

The item row does too much

Six actions want to live on one 48 px row. Putting a button on the tile for each one is the honest first attempt, and it is why the list looks busy — the row ends up advertising five things you rarely do, and burying the one thing you do constantly.

This file works the problem from the actions rather than the pixels: what each one costs, what it conflicts with, and what the row is allowed to show. Three schemes, then a recommendation.

01 · Diagnosis

Not all six actions deserve the same access

Frequency spans three orders of magnitude. Checking things off happens forty times in a shop; reordering happens once a month, if ever. An interface that gives them equal billing is not neutral — it is wrong forty times per trip.

02 · The constraint nobody notices until it breaks

Horizontal drag is already spoken for

The shop tabs swipe. That means the list body is inside a horizontal PageView, and a horizontal drag starting on a row is ambiguous: delete this item, or go to the next shop?

Flutter's gesture arena hands a horizontal drag to the innermost competitor. With swipe-to-delete on rows, the shop swipe only works if the thumb lands in a gap between rows — which, on a full list, barely exists. The tab swipe silently becomes unreliable, and it will read as a bug, not a trade.
Vertical drag has the same problem
Pasta
Milk
A drag handle makes vertical dragging mean reorder inside a list whose whole job is to scroll vertically. It works only because the handle is a tiny exempt strip — which is exactly why handles must be aimed at, and why they fail one-handed in motion.
What follows
Both drag axes are load-bearing for navigation. So the row gets no drag gestures in its default state — not swipe-to-delete, not drag-to-reorder.
That sounds like a loss. It is the opposite: it frees both axes for navigation, and forces the rare actions into a mode where they can be labelled instead of guessed.

06 · Build notes

What this means in Flutter

The row
One InkWell with onTap and onLongPress — and that is the whole gesture surface. No Dismissible, no GestureDetector on children, no nested onHorizontalDragUpdate. Nothing competes in the arena, so the PageView and the ListView both keep their axis unconditionally.
The check circle draws state but is not separately tappable — it sits inside the row's ink, so a tap near it still toggles. One handler, not two.
The menu
An OverlayEntry anchored to the row's RenderBox, not a route or a bottom sheet — that is what keeps the row in place under your thumb and the list visible behind it. Flip the menu above the row when it would fall off the bottom.
Stepper taps mutate straight through and the overlay stays up; menu taps dismiss first, then act.
The modes
One enum on the screen — browse · select · rearrange — drives the header, the tabs' physics, the FAB's scale and the row's tap meaning together. Swapping ListView for ReorderableListView happens on that enum, so handles cannot leak into browse.
Back / swipe-back exits a mode before it pops the route. Both modes also exit on their own after the list scrolls away, so nobody gets stranded.
Deletion
Delete removes locally and shows the undo snackbar; the write to Firestore fires only when the snackbar expires. Nothing needs a confirm dialog, because nothing is irreversible for four seconds.
This is what buys us the right to have no confirm step on a destructive menu item.
